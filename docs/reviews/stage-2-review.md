# Ревью этапа 2: рабочий дракончик, растительность, облака, синее небо

Критик: Opus. Объект: незакоммиченная реализация плана `docs/plans/stage-2-dino-world.md`.

## Вердикт

Ядро работает: цикл, прыжок с переменной высотой, присед, ускоренное падение, смерть, блокировка рестарта
на 400 мс, рестарт с клавиатуры и мышью, пауза по `blur` - все воспроизведено в браузере. Гарантия
проходимости выполняется (проверено симуляцией с реальным кодом). `typecheck`, `lint`, 21 тест и `build`
проходят. Контраст HUD с запасом.

Не принято из-за одного блокирующего пункта: на дробном масштабе пиксели мира получаются разной ширины
(1 и 2 физических пикселя), а это прямо нарушает критерий приемки "нет размытия и дрожания на дробном
масштабе". Кроме того, есть важные проблемы с тач-управлением и мобильной раскладкой.

Счет: блокирующих 1, важных 5, желательных 8.

## Блокирующие

### Б1. Дробный масштаб дает пиксели разной ширины

- Где: `src/render/viewport.ts:14` (выбор `pixelScale`), `src/render/renderer.ts:67-68` (одноступенчатый
  `drawImage` буфера мира с `imageSmoothingEnabled = false`).
- Что: при окне 934x1224 CSS и DPR 1 масштаб 1.503 (целый 1 дает заполнение 0.665 < `minIntegerFill`
  0.8, поэтому берется дробный). Строка канваса через дракончика и землю: серии одинакового цвета длиной
  `2 4 2 4 ... 3 1 3 2 1 2 ...`, гистограмма коротких серий `{1: 69, 2: 57, 3: 5}` - пиксель мира
  рисуется то одним, то двумя физическими пикселями [факт, замер `getImageData`]. При скролле мира
  одни и те же спрайты меняют ширину столбцов от кадра к кадру - это и есть "дрожание" [гипотеза,
  следствие замера]. На мобильном пресете масштаб целый (1), там проблемы нет, зато см. В4.
- Правка: когда `pixelScale` не целый, рисовать в два прохода:
  1. Второй offscreen-канвас размером `WORLD * N`, где `N = Math.ceil(pixelScale)`; в него мир с
     `imageSmoothingEnabled = false` (целое увеличение, все пиксели равные).
  2. Из него в основной канвас до `bufferWidth x bufferHeight` с `imageSmoothingEnabled = true` и
     `imageSmoothingQuality = 'high'`.
  Края пикселей смягчаются максимум на 1 физический пиксель, зато все пиксели одного размера и нет
  мерцания при движении. Промежуточный канвас создавать в `resize`, не в `render`. При целом масштабе
  оставить текущий одноступенчатый путь. Проверка: тот же замер серий на 934 px - короткие серии только
  одной длины плюс переходные полутона.

## Важные

### В1. Свайп вниз для ускоренного падения на таче вызывает лишний прыжок после приземления

- Где: `src/core/input.ts:87-100` (`touchstart` всегда шлет `JumpDown`), `src/game/dino.ts:42-45, 60-69`
  (буфер прыжка 0.1 с).
- Что: свайп начинается с `touchstart`, который ставит буфер прыжка. Ускоренное падение приземляет
  дракончика быстрее 100 мс, и буферизованный прыжок срабатывает сразу при касании земли. Симуляция:
  свайп на шаге 28 и 30 полета - повторный прыжок, на шагах 10-25 - нет [факт]. В браузере: свайп, когда
  дракончик ниже 20 px на спуске, - отскок после приземления [факт]. Игрок хотел быстрее приземлиться, а
  получил прыжок, часто прямо в следующий кактус.
- Правка: добавить в `Dino` метод `pressDuck()`: `duckHeld = true; jumpBuffer = 0;`, и вызывать его в
  `state.ts:123-125` вместо прямой записи `duckHeld = true`. Отпускание (`DuckUp`) оставить как есть.

### В2. Прыжок при удержанном приседе дает микропрыжок на 13.7 px

- Где: `src/game/dino.ts:71-78` (`duckHeld` имеет приоритет над удержанием прыжка с первого кадра полета).
- Что: держишь ArrowDown на земле, жмешь Space - взлет с гравитацией x3, высота 13.7 px [факт, симуляция
  и браузер]. Это ниже малого кактуса (28 px), то есть гарантированная смерть. Ситуация частая: игрок
  ускоренно падает с зажатой стрелкой вниз и жмет прыжок к следующему кактусу до того, как отпустил
  стрелку (перекрытие клавиш).
- Правка: ускоренное падение - только когда присед нажат уже в воздухе. В `Dino` завести флаг
  `fastFalling`: при взлете `fastFalling = false`; в `pressDuck()` - `if (!grounded) fastFalling = true`;
  в `update` множитель `fastFallMultiplier` применять при `fastFalling`, а не при `duckHeld`; при
  приземлении `fastFalling = false`. Присед на земле по-прежнему по `duckHeld`. Добавить тест в
  `tests/dino.test.ts`: прыжок с удержанным приседом по высоте равен обычному прыжку.

### В3. На таче присесть на земле невозможно

- Где: `src/core/input.ts:87-115`.
- Что: любой свайп начинается с `touchstart` -> прыжок, поэтому свайп вниз дает только ускоренное
  падение из невысокого прыжка, а позу приседа на земле тачем получить нельзя [факт: в браузере
  `touchstart` сразу поднял дракончика в воздух; по коду иного пути нет]. Сейчас без птиц это не мешает
  игре, но критерий приемки "присед работает" на таче не выполнен, и на этапе с птицами это станет
  блокером. Так задумано в плане, поэтому решение нужно согласовать до этапа с птицами.
- Правка (рекомендуемая): если `DuckDown` пришел, пока дракончик в воздухе меньше 0.1 с после взлета
  (ввести `airTime` в `Dino`, сбрасывать при взлете), отменить прыжок: `y = 0`, `vy = 0`,
  `grounded = true`, `jumpBuffer = 0`. Тогда быстрый свайп вниз с места = присед, а свайп в полете =
  ускоренное падение. Порог вынести в `config.ts` (`TOUCH.duckCancelJumpTime`). Альтернатива, если
  отмена визуально дергается: нижняя треть экрана = присед, остальное = прыжок.

### В4. На телефоне в портрете игра занимает 300x75 CSS px, а тап работает только по этой полосе

- Где: `src/render/viewport.ts:14`, `src/core/input.ts:35-39`, `src/style.css:26-33`.
- Что: пресет 375x812 @2x: `raw = 343*2/600 = 1.14`, целый масштаб 1 проходит порог 0.8, итог канвас
  600x150 физических = 300x75 CSS [факт]. Дракончик около 14 CSS px, кактус 7x14 CSS px; полоса занимает
  80% ширины и 9% высоты экрана. Касание за пределами канваса игнорируется - на `#stage` тап не запустил
  игру [факт]. На телефоне палец естественно попадает куда угодно.
- Правка:
  1. В `computeViewport` применять целочисленную привязку только при `integer >= 2`; при меньшем -
     дробный масштаб (с двухпроходной отрисовкой из Б1). На 375 px канвас станет 343 CSS по ширине.
  2. Тач-обработчики (`touchstart/move/end/cancel`) вешать на `#stage` (или `document`), а не на канвас;
     `touch-action: none` перенести на `html, body` / `#stage`. Клик мышью оставить на канвасе (для
     иконки рестарта нужны координаты в мире).
  3. При `(pointer: coarse) and (orientation: portrait)` показывать в HUD подсказку "Поверните
     телефон" под основной надписью на старте - в ландшафте мир 4:1 занимает экран намного лучше.

### В5. Нет интерполяции рендера: на мониторе 144 Гц движение рывками

- Где: `src/core/loop.ts:57-58`, `src/render/renderer.ts:49-70`.
- Что: логика шагает 60 Гц, rAF в тестовой панели дал 73 кадра за 500 мс (около 146 Гц) [факт]. Без
  интерполяции каждый логический шаг показывается то 2, то 3 кадра подряд (144/60 = 2.4), мир на
  скорости 320-640 px/с дергается неравномерными ступенями [гипотеза: глазом на 144 Гц не проверял, вывод
  из кода и частоты rAF]. Это тоже подпадает под "нет дрожания".
- Правка: `FixedStepper.advance` возвращает `alpha = accumulator / step`, `GameLoop` передает его в
  `render(alpha)`. В объектах хранить предыдущую позицию (`prevX` у `Obstacle` и `LayerItem`, `prevY` у
  `Dino`, `prevGroundOffset` у `Game`), обновлять ее в начале шага логики, в `drawSprite` рисовать
  `Math.round(prev + (cur - prev) * alpha)`. Для только что заспавненных объектов `prevX = x`. Без
  аллокаций - только поля.

- Правка: в `spawner.ts:52` убрать лишний `width` (или явно записать в план, что зазор считается от

### Блокирующие

#### Р2-Б1. Нажатие "вниз" в первые 100 мс после прыжка на клавиатуре отменяет прыжок и телепортирует на землю

- Где: `src/game/dino.ts:66-81` (`pressDuck` отменяет прыжок при `airTime < TOUCH.duckCancelJumpTime`
  независимо от источника ввода), `src/game/state.ts:148-149`.
- Что: в браузере Space, затем ArrowDown через 78 мс после взлета - `y` с 32.1 сразу 0, поза приседа
  [факт]. Высота в момент отмены: 21.8 px на 50 мс, 34.5 px на 80 мс, 40.3 px на 95 мс [факт,
  симуляция]. Окно успешного взлета над одиночным кактусом, если "вниз" нажат через 50/80/95 мс после
  тапа: 0 мс для малого и большого кактуса на 320 и для большого на 640, 0-33 мс для малого на 640
  (без "вниз" - 217-317 мс) [факт, симуляция]. "Прыжок и сразу вниз" - обычный прием для короткого
  прыжка с ускоренным падением, и в раунде 1 он работал; теперь он гарантированно убивает, а скачок на
  30-40 px вниз выглядит как баг. Плюс новая лазейка: ранний прыжок можно "отозвать" стрелкой вниз и
  прыгнуть заново.
- Правка:
  1. Отмену разрешить только для тача: в `Input` пушить отдельный тип `InputType.SwipeDown` из
     `onTouchMove` (клавиатура остается `DuckDown`), в `Game.handleInput` для `SwipeDown` вызывать
     `dino.pressDuck(true)`, для `DuckDown` - `dino.pressDuck(false)`; ветку отмены в
     `pressDuck(allowCancel)` выполнять только при `allowCancel`. `DuckUp` для обоих один.
  2. И для тача ограничить отмену высотой, а не только временем: `if (allowCancel && this.y <=
     TOUCH.duckCancelMaxHeight)` (около 16 px, в `config.ts`), иначе ускоренное падение. Так уходит
     заметный скачок с 20-40 px.
  3. Тест в `tests/dino.test.ts`: `pressDuck(false)` через 5 шагов после взлета - дракончик остается в
     воздухе с `fastFalling = true`.
